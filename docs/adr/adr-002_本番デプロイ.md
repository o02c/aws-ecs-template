# ADR: ECRイメージのクロスアカウント昇格方式

- Status: Accepted
- Date: 2026-03-22
- Deciders: TBD
- Tags: aws, ecr, codebuild, cicd, security, release

## Context

!!以下はあくまで抽象的な議論なので細かい名称は未定!!

stg アカウントでビルド・検証したコンテナイメージを、再ビルドせずに prd アカウントへ昇格したい。  
対象は Amazon ECR のプライベートリポジトリであり、初期実装は CodeBuild による実行を想定する。

AWS の Container Build Lens では、イメージは一度だけビルドし、同一イメージを次の環境へ昇格させる運用が推奨されている。これにより、環境ごとの差分混入を減らし、一貫性を高められる。 :contentReference[oaicite:0]{index=0}

また、クロスアカウントアクセスは IAM ロールの AssumeRole による委譲が基本パターンであり、恒久的な認証情報ではなく一時クレデンシャルを用いる構成が推奨される。 :contentReference[oaicite:1]{index=1}

今回の論点は以下である。

- stg 側から prd 側 ECR に直接 push させるか
- prd 側の権限境界で昇格を実行するか
- 初期実装として CodeBuild をどのアカウント側の主体として動かすか

## Decision

以下を採用する。

### 1. 昇格方式
stg 側 ECR のイメージ manifest を取得し、prd 側 ECR に `PutImage` することで昇格する。  
Docker pull/push による再転送ではなく、**manifest コピー方式**を採用する。

### 2. 権限境界
**prd アカウント側に昇格専用 IAM ロール `EcrPromoteRole` を作成する。**  
CodeBuild はこのロールを利用して昇格処理を実行する。

思想としては、**「本番に何を入れてよいか」の最終決定権を prd 側に置く**。

### 3. 実行主体
初期は **CodeBuild により昇格ジョブを実行する**。  
CodeBuild の配置場所は prd アカウント、または CI/CD 用アカウントのいずれでもよいが、少なくとも **実行時に利用する昇格権限は prd 側で管理されるロールに集約する**。

### 4. 権限方針
`EcrPromoteRole` には、必要最小限の権限のみを付与する。

- stg 側 ECR リポジトリに対する読み取り
  - `ecr:BatchGetImage`
  - `ecr:DescribeImages`
- prd 側 ECR リポジトリに対する書き込み
  - `ecr:PutImage`
  - 必要に応じて `ecr:DescribeRepositories`
- 認証用
  - `ecr:GetAuthorizationToken`

ECR では push や pull の認証に `ecr:GetAuthorizationToken` が必要であり、push 系操作には個別の IAM 権限が必要となる。 :contentReference[oaicite:2]{index=2}

### 5. 非採用方針
stg 側の通常 deploy/build ロールに、prd 側 ECR への `PutImage` 権限は付与しない。

## Rationale

### A. build once, promote many に適合する
同一 digest のイメージをそのまま次環境へ昇格できるため、stg で検証した成果物と prd に投入する成果物を一致させやすい。  
これは AWS の推奨する「一度ビルドしたイメージを各環境へ昇格する」方針に合致する。 :contentReference[oaicite:3]{index=3}

### B. 本番権限を stg 側に持たせない
stg 側から直接 prd に push できる設計は、stg 側の CI/CD、ランナー、運用者の権限がそのまま本番レジストリへの書き込み能力につながる。  
これでは責務分離が弱く、侵害時の影響範囲も広がる。

一方、prd 側で管理する `EcrPromoteRole` に集約すれば、**本番投入権限を本番側の境界で閉じられる**。

### C. IAM ロール委譲の基本パターンに沿う
AWS は、アカウント間アクセスを IAM ロールで委譲するパターンを基本としている。  
この方式は恒久クレデンシャルの配布を避けられ、監査および権限管理がしやすい。 :contentReference[oaicite:4]{index=4}

### D. ECR のアクセス制御モデルと相性がよい
ECR は IAM の identity-based policy と repository policy / registry policy を組み合わせてアクセス制御できる。  
そのため、昇格専用ロールに必要最小限の権限を与え、対象リポジトリ側でも必要に応じてアクセス境界を設けられる。 :contentReference[oaicite:5]{index=5}

## Options Considered

## Option 1: stg 側ロールから prd 側 ECR に直接 push する
### Pros
- 実装が単純
- 初期構築コストが低い

### Cons
- stg 側の build/deploy 権限が prd への書き込み権限を持つことになる
- 本番権限の境界が曖昧になる
- 監査、承認、権限制御を prd 側で閉じにくい

### Judgment
非採用。  
簡便だが、責務分離と最小権限の観点で弱い。

## Option 2: prd 側の昇格専用ロールで manifest コピーを行う
### Pros
- 本番投入権限を prd 側で管理できる
- build once, promote many を満たせる
- digest 単位で昇格管理しやすい
- CodeBuild と相性がよい

### Cons
- クロスアカウントの IAM / ECR 権限設計が必要
- 初期設定は Option 1 よりやや複雑

### Judgment
採用。

## Option 3: ECR クロスアカウントレプリケーションを使う
### Pros
- 自動同期が可能
- 複製用途には向く

### Cons
- 「承認したものだけ prd に昇格する」という release 制御に不向き
- 有効化前の既存イメージは自動複製されない
- 昇格イベントを明示的に扱いにくい :contentReference[oaicite:6]{index=6}

### Judgment
非採用。  
今回の目的は同期ではなく、承認を伴う昇格であるため。

## Consequences

### Positive
- stg で検証済みのイメージをそのまま prd に反映できる
- 本番投入権限を prd 側に限定できる
- 承認フローや監査ログを本番側主体で設計しやすい
- 後続で GitHub Actions や OIDC ベースの実行主体へ移行しやすい

### Negative
- クロスアカウントの IAM / ECR ポリシー設計が必要
- CodeBuild の assume role / 権限移譲設計がやや複雑
- multi-arch イメージや manifest list を扱う場合はテストが必要

### Neutral
- 将来的に CodeBuild 以外の実行基盤へ移しても、`prd 側に PromoteRole を置く` という基本方針は維持できる
- 初期は手動承認 + CodeBuild 実行でもよく、後から自動化段階を上げられる

## Operational Notes

### 推奨フロー
1. stg アカウントでイメージを build / push する
2. stg 環境で deploy / verify を行う
3. 承認後、CodeBuild が `EcrPromoteRole` を用いて manifest を取得する
4. prd 側 ECR に同一 manifest を `PutImage` する
5. prd 側では release 用タグを付与し、その tag または digest を用いて deploy する

### タグ運用
可変タグのみでの昇格は避け、**digest を正本**として扱う。  
タグは視認性向上のために併用する。

例:
- stg: `git-<commit-sha>`
- prd: `release-YYYYMMDD-NN`

### ロール分離
- stg の build/deploy ロール
- prd の promote ロール
- prd の deploy ロール

は分離する。  
特に、stg の通常運用ロールから prd ECR へ直接書き込めないことを保証する。

## Future Considerations

- CodeBuild から OIDC 対応の外部 CI/CD 実行基盤へ移行する場合も、信頼先を差し替えるだけでよい構成にしておく
- 承認ステップを CodePipeline や GitHub Environments などへ拡張可能にしておく
- Terraform により `EcrPromoteRole`、ECR repository policy、CodeBuild project をコード化する
