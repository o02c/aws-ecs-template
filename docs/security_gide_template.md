# 第1章. はじめに

本システムはAWS上に構築する全社/部門システムが最低限実装すべきセキュリティ機能を、システム部門が統一的に管理する環境を提供する。  
本書では、本システムの運用に関わる制限事項や運用作業について記載する。

## 1.1. 前提条件

- 本書に記載する内容はNTTデータからMSA様に対して提示が必要な事項とし、全社/部門システムの担当者（以下、全社/部門システム担当者）に向けた内容だけでなく、システム部門の担当者（以下、システム部門ユーザ）に関わる内容を含めた記載とする。

## 1.2. 制限事項

- 本システムでは一定のセキュリティを担保するために、禁止事項に対してSCPによるAPI発行の禁止、またはConfig / IAM Access Analyzerによる設定状態の検知を行う。
- 禁止、または検知の対象は全社/部門システム用アカウントのみとし、原則として個別許可は行わない。（標準環境管理アカウントにおいてもIAM Access Analyzerによる検知は有効） # TODO: これの意味が不明
- 全社/部門システム用アカウントにおいて個別に許可を行うことが可能な要素については、第2章に記載する。

# 第2章. 標準環境における禁止事項

標準環境において、全社/部門システム担当者に対して禁止する操作を記載する。  
禁止操作に関しては、システム的に禁止行為を統制しているものと、システム的には統制していないが、システム部門ユーザによる目視確認やガイドラインでのアナウンスなどの手動運用により統制しているものの二種類に分類されるため、項目を分けて記載している。  
なお、他AWSアカウントから全社/部門システム用アカウントへのアクセスの統制に使用するサービスの一つとしてIAM Access Analyzerがあるが、IAM Access Analyzerの検知については、後述の統制対象サービス以外のAWSサービスも対象となる。  
本禁止事項は標準環境においてシステム的な禁止/検知、または目視確認により制限する内容となり、全社/部門システムのシステム構成に応じて別途MSA様のセキュリティ関連チェックシートへの準拠が必要となる。  
全社/部門システム担当者によって対応が必要な項目については、以下のセキュリティ関連チェックシートを参照し確認すること。

1. サイバーセキュリティ対策状況チェックリスト
2. クラウドサービスチェックシート
3. 部門システムチェックシート ※部門システムの場合に確認
4. システムセキュリティ管理細則確認シート
5. クラウド設定点検シート（※）  
   ※「3.3.17. SecurityHubコントロールへの準拠」にSecurityHubコントロールに非準拠となっている設定への対応時の注意事項が記載されているため、参照すること。
6. セキュリティ要件シート

## 2.1. 共通的な禁止事項

AWSアカウントで行う操作のうち、全社/部門システム担当者に対して共通的に禁止する操作を以下に記載する。

### 1) SCP・Config・IAM Access Analyzer・Firewall Managerによってシステム的な統制がかけられている禁止行為

- AWSアカウント外部へのデータ持ち出しを制限するため、個別許可されたAWSアカウントを除き、全ての他AWSアカウントのリソースに対するAPIアクションを禁止  
  ※アカウントにアタッチされたSCPの設定を変更することで、個別に許可することが可能  
  ※以下の操作については禁止の対象外とする。  
  - Amazon / AWS Marketplaceが他AWSアカウント内で管理しているAMIを用いたEC2インスタンスの作成
  - AWSが管理しているアカウント上に存在する、GuardDutyのランタイムモニタリングが動作するために必要なECRイメージの参照
- 情報の機密性を担保するため、日本リージョン以外でAWSリソースを作成することの禁止
- 不正アクセスの可能性を低減するため、MS1ネットワーク内IPアドレス、およびAWSアカウント払い出し時の申請に基づき個別に許可したIPアドレス以外からのAWSリソースへのアクセスの禁止  
  【クラウドサービスチェックシート項番205, 206, 207, 208, 219, 220, 221, 229に基づく対応】  
  ※アカウントにアタッチされたSCPの設定を変更することで、個別に許可することは可能
- 東京リージョンの利用を前提とし大阪リージョンは遠隔地保管目的の利用のみとするため、一部のサービス（S3, KMS, Backup, GuardDuty, SecurityHub, IAM Access Analyzer, SNS）を除き大阪リージョンにおける操作を禁止
- 不正アクセスの可能性を低減するため、AWSアカウント内で保管している業務データを外部からAPIアクセス可能な設定にすることを禁止

### 2) システム的な統制はかけられていないが、システム部門ユーザによる目視確認やガイドラインでのアナウンスにより統制を行う禁止行為

- 標準環境で作成したリソースと全社/部門システム担当者が独自に作成したリソースを識別しやすくするため、全社/部門システム担当者が標準環境と同じ命名規則を利用してAWSリソースを作成することの禁止  # TODO: 命名規則の記載なし、また「標準環境と同じタグ」の記載なし
  ※全社/部門システム担当者が利用するガイドラインで標準環境と同じタグを付与しないように周知する。
- リソースタグを用いて標準環境内リソースの統制を行っているため、全社/部門システム担当者がAWSリソースに対し、標準環境と同じリソースタグを付与することの禁止   # TODO: 「標準環境と同じリソースタグ」の記載なし
  ※全社/部門システム担当者が利用するガイドラインで標準環境と同じタグを付与しないように周知する。
- AWSアカウント内で保管している業務データを外部に持ち出すことの禁止  
  ※インターネット経由での持ち出しに関しては統制をかけていないが、全社/部門システム担当者が利用するガイドラインでAWSアカウントに保管している業務データを外部に持ち出さないように周知する。

## 3.1. アカウント払い出しフロー

## 3.2. システム部門による初期環境設定

### 3.2.1. ルートユーザを用いた初期設定

#### 1) IAMユーザ/ロールによる請求情報へのアクセス有効化

- ルートユーザで全社/部門システム用アカウントにログインし、Billingのコンソール画面に移動後、「IAM ユーザおよびロールによる請求情報へのアクセス」を修正し、「IAMアクセスのアクティブ化」にチェックを入れる。

#### 2) デフォルトVPCの削除

- VPCを利用する場合は標準環境が提供するテンプレートでVPCを作成するため、デフォルトVPCの削除を行う。
- ルートユーザで全社/部門システム用アカウントにログインし、東京リージョンと大阪リージョンのデフォルトVPCを選択し、削除する。

#### 3) Organizations組織の設定

- 標準環境管理アカウントにログインし、標準環境管理者用ロールにスイッチロールした後、Organizationsコンソール画面から全社/部門システム用アカウントに組織への招待を送信後、ルートユーザで全社/部門システム用アカウントにログインし、Organizationsコンソール画面で招待を承認する。  
- Organizations組織への参加完了後、標準環境管理アカウントにログインし、標準環境管理者用ロールにスイッチロールした後、Organizationsコンソール画面から全社/部門システム用アカウントのOU移動およびアカウントのタグ付けを実施する。

  - 標準環境で作成されたリソースを識別するために、CloudFormationで作成されたConfigルールにタグを付与する
- **Amazon Inspectorの有効化**  
  - Amazon Inspectorのコンソール画面から、「Inspectorをアクティブ化」を選択し、Inspectorを有効にする
- **EventBridgeルールへのタグ付け**  
  - 標準環境で作成されたリソースを識別するために、CloudFormationで作成されたEventBridgeルールにタグを付与する
- **SecurityHubセキュリティ基準の有効化、検出結果の集約設定**  
  - セキュリティ基準 CIS AWS Foundations Benchmark v1.4.0 を有効化する  
  - 大阪リージョンの検出結果を東京リージョンへ集約するために、「検出結果の集約設定」を編集する
- **全社/部門システム用アカウントにアタッチされるSCPのポリシー変更**  
  - 環境払出申請に基づきセキュリティ緩和措置を実施する場合、SCPのポリシー変更を行う
- **Configサービスロールの作成**  
  - AWS Configのコンソール画面から、Configの設定画面を開き、レコーダの設定からConfig用サービスロールを作成する

## 3.3. 全社/部門システムにおいて対応が必要な設定

### 3.3.1. VPCの作成

VPCを利用する場合は、全社/部門システム担当者が標準環境の用意したテンプレートを用いてVPC関連リソースを作成する。  
作成されるVPCは、エンドポイント用サブネットはSingle-AZ構成では1サブネット16IPアドレスを利用し、Multi-AZ構成では2サブネット32IPアドレスを利用する。  
同様にNetwork Firewall用サブネットもSingle-AZ構成では1サブネット16IPアドレスを利用し、Multi-AZ構成では2サブネット32IPアドレスを利用する。  
VPCリソースを作成するテンプレートはインターネット接続無OU用VPCのテンプレートと、インターネット接続有OU用VPCのテンプレートが存在しており、システムのインターネット利用の有無により適用するテンプレートを使い分ける。  
なお、インターネット有OU用VPCのテンプレートは、インターネット無OU用VPCのテンプレートで作成したリソースに対して設定やリソースを追加するテンプレートであるため、3.3.1.1 および 3.3.1.2 の手順でインターネット無OU用VPCを作成した後、3.3.1.3 ～ 3.3.1.5 の手順でインターネット有OU用VPCのリソース作成を行う。

#### 3.3.1.1. Cloud Formationを用いた初期設定

1) インターネット接続無OU用VPC関連リソース作成を行うために、全社/部門システム担当者は標準環境のテンプレートからStackを作成する。

- ① **VPC用スタックの作成**  
  `private_ou_vpc.yaml` を使用してStackを作成する
- ② **VPC内リソース用スタックの作成**  
  `private_ou_vpc_resource.yaml` を使用してStackを作成する
- ③ **エンドポイントのルートテーブル用スタックの作成**  
  `private_endpoint_route.yaml` を使用してStackのテンプレートを変更する

#### 3.3.1.2. 手動による初期設定

1) VPCのコンソール画面から以下の設定を行う。

- ④ **デフォルトNetworkACLへのサブネット関連づけ**  
  明示的なサブネットの関連付けが存在しないNetworkACLはクラウド設定点検シート（AWS用）のチェック項目（VPC-2-4）に非準拠となるが、デフォルトNetworkACLは削除不可能なため、サブネットの関連付けを行う
- ⑤ **デフォルトNetworkACLのルール変更**  
  デフォルトのルールではすべての通信が許可されており、クラウド設定点検シート（AWS用）のチェック項目（EC2-2-7）に非準拠となるが、デフォルトNetworkACLのルールは削除不可能なため、設定変更を行う
- ⑥ **デフォルトセキュリティグループのルール削除**  
  デフォルトのセキュリティグループルールが存在している場合、クラウド設定点検シート（AWS用）のチェック項目（VPC-2-6）に非準拠となるが、CloudFormationによるデフォルトセキュリティグループのルールを削除することは不可能なため、ルール削除を行う
- ⑦ **VPCエンドポイントへのタグ付け**  
  標準環境で作成されたリソースを識別するために、CloudFormationで作成されたVPCエンドポイントにタグを付与する

#### 3.3.1.3. インターネット接続有VPCを作成する場合のCloud Formationを用いた初期設定

1) インターネット接続有VPCを作成する場合、3.3.1.1、3.3.1.2 の手順を実施する。  
2) インターネット接続有VPC関連リソース作成を行うために、全社/部門システム担当者は標準環境のテンプレートからStackを A)～D) の順番で作成する。

- ⑧ **VPC内リソース（インターネット接続に必要なリソース）用スタックの作成**  
  `public_ou_vpc_resource.yaml` を使用してStackを作成する
- ⑨ **VPC用スタックのテンプレート変更**  
  `private_ou_vpc.yaml` を用いて作成したStackのテンプレートを、`public_ou_vpc.yaml` に変更する
- ⑩ **エンドポイントのルートテーブル用スタックのテンプレート変更（1度目）**  
  `public_endpoint_route.yaml` を使用してStackを作成する
- ⑪ **IGW用ルートテーブル用スタックの作成**  
  `public_ou_igw_route.yaml` を使用してStackを作成する

#### 3.3.1.4. インターネット接続有VPCを作成する場合の手動による初期設定

1) VPCのコンソール画面から以下の設定を行う。

- ⑫ **Network Firewall用ルートテーブルのルート設定**  
  Firewall Managerにより自動生成されたルートテーブルに、InternetGatewayへのルートを設定する
- ⑬ **InternetGateway用ルートテーブルのルート設定**  
  Network FirewallのエンドポイントIDを指定してルートを設定する
- ⑭ **DNS Firewallのクエリログ設定へのタグ付け**  
  標準環境で作成されたリソースを識別するために、CloudFormationで作成されたクエリログにタグを付与する
- ⑮ **Network Firewallログ出力設定**  
  Network Firewallのログ記録からアラートログとフローログを監査ログ用バケットに送信する設定を行う

#### 3.3.1.5. インターネット接続有VPCを作成する場合のCloud Formationを用いた後処理

- ⑯ **エンドポイントのルートテーブル用スタックのテンプレート変更（2度目）**  
  エンドポイントサブネット用ルートテーブルのルート設定はFirewall ManagerによるNetwork Firewall自動デプロイにパブリックサブネットを作成する必要があるために行う設定であり、Network Firewallデプロイ後には不要な設定なので、インターネット接続無OU用VPCのエンドポイントサブネット用ルートテーブルを作成するテンプレートによりスタックを更新することでルート設定を削除する。

### 3.3.2. WAFログ出力設定

- ⑰ **WAFのログ出力設定**  
  Webアプリケーション等を提供するシステムではWAFの適用を必須とするためにCloudFront利用が必要となる。WAF（Web ACL）を通過したすべてのトラフィックを記録するために、WAF（Web ACL）のフローログ記録を有効にする。  
  WAF（Web ACL）のログ出力は、標準環境が用意したバージニアリージョンのAmazon Data Firehoseを介して、東京リージョンのAmazon S3へと連携する。

### 3.3.3. S3サーバーアクセスログの出力設定

- ⑱ **S3サーバーアクセスログの出力設定**  
  東京リージョンで業務用にS3バケットを利用する場合は、アクセスの監査やセキュリティ対策のためにサーバーアクセスログ取得設定を行う。  
  業務用S3バケットのサーバーアクセスログは、出力先として標準環境が用意したサーバーアクセスログ用バケットを設定する。

### 3.3.8. データ、コンフィグのバックアップ

1) 全社/部門システムが作成した業務用リソースやそのデータのバックアップの実施は必要だが、バックアップに用いるサービスや方法は任意とする。

2) 遠隔地バックアップを実施する場合は利用可能リージョンの制約上、大阪リージョンへのみバックアップ可能となる。  
なお、大阪リージョンは大部分のサービスについて操作を禁止としているため、バックアップに用いることが可能なサービスはS3やAWS Backupなど一部のサービスに限られる。

### 3.3.9. VPCエンドポイントの作成

1) VPCエンドポイントを作成するにあたり、VPCエンドポイントを介した他AWSアカウントへのデータ持ち出しを防ぐために、他AWSアカウントのプリンシパルを拒否するポリシーを記述する必要がある。  
エンドポイントポリシー変更の対象となるVPCエンドポイントは、一部のVPCエンドポイントポリシー非対応のサービスを除く、AWSサービス宛てのVPCエンドポイントであり、マネジメントコンソールからVPCエンドポイントポリシーの編集画面が表示できるVPCエンドポイントとなる。  
VPCエンドポイントポリシーには、以下の記述を `Statement` セクション内に追加する。

```json
{
  "Sid": "DenyOtherAwsAccountPrincipals",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "*",
  "Resource": "*",
  "Condition": {
    "StringNotEquals": {
      "aws:PrincipalAccount": [
        "<自AWSアカウントID>",
        "<許可するAWSアカウントID>"
      ]
    }
  }
}
```

### 3.3.12. WAF / Network Firewall / DNS Firewall の許可/拒否設定について

#### 1) WAF

WAFはWebアプリケーション等を提供するシステムにおいてWebアプリケーションを攻撃から保護するために利用する必要がある。  
WAFのWeb ACLはFirewall Managerによって統制され、ホワイトリスト形式でウェブリクエスト制御を行うため、許可設定を行わない限り全ての通信が拒否される。  
全社/部門システム担当者はシステム要件に応じてWeb ACLに個別の許可/拒否を行うルールグループを作成し、このルールグループをWeb ACLに追加することでウェブリクエストの制御を行う。  
※CloudFrontに適用されているWeb ACLは、CloudFrontディストリビューションのセキュリティ設定画面より確認可能。

- WAF WebACL 開発者ガイド

#### 2) Network Firewall

Network Firewallはインターネット接続有VPCにおいてVPCとインターネット間で通信を行う際に利用する必要がある。  
Network FirewallはFirewall Managerによって統制され、ホワイトリスト形式でVPCのアクセス制御と保護を行うため、許可設定を行わない限り全ての通信が拒否される。  
Network Firewallは手順 3.3.1.3 の手順でパブリックサブネットをデプロイした際に、Firewall Managerによって自動的に作成され、全社/部門システム担当者はシステム要件に応じてNetwork Firewallポリシーの許可/拒否を行うルールグループを作成し、このルールグループをNetwork Firewallのファイアウォールポリシーへ追加することでVPCとインターネット間のアクセス制御を行う。  
※VPC内で使用されているNetwork Firewallは、VPC画面内、Network Firewallのファイアウォール画面よりNetwork Firewallの名前を選択することで、関連付けられたVPCやサブネットを確認可能。

- AWS Network Firewall ルールグループ 開発者ガイド

#### 3) DNS Firewall

DNS Firewallはインターネット接続有VPCにおいてVPCのDNSトラフィックをフィルタリング及び規制するために利用する必要がある。  
DNS FirewallはFirewall Managerによって統制され、ホワイトリスト形式でDNSトラフィックの制御を行うため、許可設定を行わない限り全てのDNSクエリが拒否される。  
また、既知の悪意のあるドメイン等へのアクセスを防止するために、AWSマネージドドメインリストが強制的に適用され、該当するDNSクエリは拒否される。  
DNS FirewallによりDNSクエリのフィルタは、Route53 Resolverに対するDNSクエリが対象となるため、インターネット接続有VPC内の名前解決はインターネット宛の通信か内部宛の通信かに関わらず、DNS Firewallによりフィルタされる。  
このため、インターネット接続有VPC内で名前解決を行う場合には全社/部門システム担当者がシステム要件に応じてDNS Firewallの許可/拒否を行うルールグループやドメインリストを作成し、VPCへの関連付けを行う必要がある。  
※AWSサービス（EC2インスタンスやVPCエンドポイント等）に自動的に割り当てられるDNS名の解決を行う場合にも許可設定が必要。

強制的に適用される拒否ルールには、以下のAWSマネージドドメインリストが適用される。

- `AWSManagedDomainsAggregateThreatList`  
  マルウェア、ランサムウェア、ボットネット、スパイウェア、DNSトンネリングなど、複数のDNS脅威のカテゴリに関連するドメイン
- `AWSManagedDomainsBotnetCommandandControl`  
  スパムマルウェアに感染したコンピュータのネットワーク制御に関連するドメイン
- `AWSManagedDomainsMalwareDomainList`  
  マルウェアの送信、ホスティング、配布に関連するドメイン

以下にAWS公式の開発者ガイドを示す。

- DNS Firewall ルール設定 開発者ガイド

なお 2024/3 現在、Firewall Managerによって統制されたDNS Firewall利用環境においてはルールグループをVPCへ関連付ける際にマネジメントコンソールからGUIでの関連付けを行うことができず、コマンドラインによる設定が必要となる。  
DNS Firewallの許可設定を行わない限りVPCエンドポイント経由したAPI実行を行うこともできないため、AWSアカウント内から設定を行うためにはCloud Shellを用いたCLIでの設定が必要となる。  
CLIによる関連付けは、以下のコマンドを実行することで可能。（改行無しの1行のコマンドとして実行する。）

```bash
aws route53resolver associate-firewall-rule-group \
  --firewall-rule-group-id <firewall-rule-group-id> \
  --vpc-id <vpc-id> \
  --priority <priority> \
  --mutation-protection DISABLED
```

CLIの利用にあたっては、クラウドサービスチェックシート項番87, 232, 233 のチェック内容を確認すること。

# 第6章. 通知メッセージ

標準環境では、マネジメントコンソールへの不正アクセスを検知した場合や、禁止としている設定がリソースやサービスに対して行われた場合、外部アクセス許可が設定された場合などのセキュリティ的な懸念が生じる状況と、CloudFormationテンプレート用バケットなどの標準環境が用意したS3バケットに格納されたデータが削除された場合や、監査レポート生成のためにAthenaのクエリが失敗した場合などの運用上の問題が発生した際に、メールによる通知を行う。

## 6.1. 不正アクセス検知

### 6.1.1. 通知概要

AWSマネジメントコンソールへの不正なログイン（試行を含む）やAWSアカウントの管理権限を有するルートユーザのログインを検知するために、該当するイベントの検知、およびメールによる通知を行う。

### 6.1.2. 検知対象一覧

監視対象とする操作が、一定時間以内に一定回数以上行われた場合にメール通知が行われる。以下に不正アクセス検知として通知される条件を示す。

| 項番 | 監視対象の操作 | メール通知のタイミング |
|---|---|---|
| 1 | 無許可のIPアドレスからのアクセス | AWSマネジメントコンソールへの許可されていないIPアドレスからのログインが行われた場合 |

# 第7章. Accepted Risks / Design Decisions

本章では、セキュリティレビューにおいて検出された指摘事項のうち、AWS仕様上の制約やアーキテクチャ上の判断により意図的に対応しないこととした項目について、その根拠とリスク受容の判断を記載する。

## 7.1. SHA-1 in CloudFront Signed URLs (Sec1)

### 指摘内容

CloudFront署名付きURLにおいてRSA-SHA1が使用されている。

### 根拠

CloudFront署名付きURLは、AWSの仕様としてRSA-SHA1による署名が必須である。代替のアルゴリズムは提供されていない。

- [Amazon CloudFront Developer Guide - Creating a signed URL using a custom policy](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-creating-signed-url-custom-policy.html) -- "Sign the policy statement using RSA-SHA1"

### リスク受容

- **受容レベル**: Low
- AWSプロトコル上の制約であり、利用者側で代替手段を選択することができない。AWS側の仕様変更を待つ以外に対応方法はない。

---

## 7.2. S3 Encryption: AES256 (SSE-S3) for logging and CI/CD buckets (Sec6)

### 指摘内容

ロギング用バケットおよびCI/CDアーティファクト用バケットにおいて、KMS (SSE-KMS) ではなくAES256 (SSE-S3) による暗号化が使用されている。

### 根拠

ALBアクセスログおよびCloudFront標準ログの配信先S3バケットは、AWSの仕様によりSSE-S3が必須または推奨されている。

- [Elastic Load Balancing - Enable access logging](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/enable-access-logging.html) -- "Amazon S3-managed encryption keys (SSE-S3)"
- [Amazon CloudFront Developer Guide - Access Logs](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/AccessLogs.html) -- "SSE-S3 only"

CI/CDアーティファクト用バケットについては、ロギングバケットとの一貫性の確保、およびCodePipelineアーティファクト暗号化固有の制約を考慮し、AES256 (SSE-S3) を採用している。

### リスク受容

- **受容レベル**: Low
- SSE-S3による保存時暗号化は引き続き提供されている。カスタマーマネージドキーによる鍵ローテーション制御は利用できないが、AWSマネージドキーによる暗号化は有効である。

---

## 7.3. Inspector: ECR only, not ECS runtime (Sec9)

### 指摘内容

Amazon InspectorによるスキャンがECRコンテナイメージのみを対象としており、ECSランタイムスキャンが有効化されていない。

### 根拠

ECSランタイムスキャンはFireLensサイドカー構成と合わせて有効化する予定であり、issue [#5](https://github.com/o02c/aws-ecs-template/issues/5) にて追跡管理されている。

### リスク受容

- **受容レベル**: Medium
- ランタイム脆弱性検出に一時的なギャップが存在する。ECRイメージスキャンによりデプロイ前の脆弱性検出は確保されているが、実行時の脆弱性検出はFireLens導入まで対応されない。

---

## 7.4. DNS Firewall disabled (Sec11)

### 指摘内容

Route 53 Resolver DNS Firewallが無効化（コメントアウト）されている。

### 根拠

本システムのVPCはプライベートサブネットのみで構成されており、インターネットへの直接のエグレスパスを持たない。ECSタスクはVPCエンドポイント経由でのみAWSサービスと通信しており、DNS exfiltrationのリスクは極めて限定的である。コスト対効果の観点から、現時点では無効化としている。

NATゲートウェイ経由での外部APIアクセスが必要となった時点で再評価を行う。

### リスク受容

- **受容レベル**: Low
- VPCエンドポイント経由の通信のみであり、DNS経由のデータ流出リスクは最小限に抑えられている。外部通信要件の追加時に再度有効化を検討する。
